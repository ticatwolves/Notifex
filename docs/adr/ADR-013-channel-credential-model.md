# ADR-013 — Channel credential model, storage and resolution

- **Status:** Accepted (2026-11-27). Approved with the Phase 2 plan.
- **Decider:** Shobhit
- **Refines:** ADR-005 (platform-managed and BYO credentials). ADR-005's decisions stand; this ADR fixes the schema, the API and the edge cases.

## Context
ADR-005 decided that each channel can use Notifex's own vendor account (platform) or the tenant's (BYO), resolved environment → application → tenant → platform at trigger acceptance, with BYO secrets encrypted under the tenant DEK. Phase 2 stores and resolves credentials; Phase 3 uses them to send.

## Decision

### 1. Table `channel_credentials`
| Column | Notes |
|---|---|
| `id` | UUIDv7; public id `crd_…` |
| `tenant_id` | TenantMixin (ADR-010) |
| `application_id` NULL, `environment_id` NULL | Scope. Composite FKs `(tenant_id, application_id)` and `(tenant_id, application_id, environment_id)`. `CHECK (environment_id IS NULL OR application_id IS NOT NULL)` |
| `channel`, `provider` | From the provider catalogue (§3) |
| `mode` | `platform` or `byo` |
| `name` | Label for humans |
| `config` | JSONB, **non-secret** settings (from address, account SID, role ARN). Validated against the provider's config schema; unknown fields rejected |
| `secret_ciphertext` | BYTEA, NULL when the provider has no secret. AES-256-GCM under the tenant DEK with the ADR-006 per-cell key; AAD = `tenant_id | row id | "secret_ciphertext"` |
| `secret_hint` | Last 4 characters of the primary secret field (`…a1b2`), for recognising which secret is set |
| `status` | `pending`, `verified`, `disabled` |
| `verified_at`, `rotated_at`, `created_at`, `updated_at` | |

**One active credential per scope and channel:** a partial unique index on `(tenant_id, application_id, environment_id, channel) NULLS NOT DISTINCT WHERE status <> 'disabled'`. Resolution is therefore deterministic, and enabling a second credential in the same scope is `409 conflict`.

### 2. Secrets are write-only
- Accepted only on create and rotate. Never returned by any endpoint, never logged, never written to audit events (audit records `secret_hint` and `rotated_at` only).
- Size: at most 16 KiB of secret JSON per credential.
- Decrypted only at dispatch time (Phase 3). The API has no decrypt path.
- Crypto-shredding the tenant (ADR-006) makes every BYO secret unreadable.
- **Rotate** replaces the secret in one statement (new ciphertext, new hint, `rotated_at`). In-flight notifications pick up the new secret, because the run snapshot stores the credential reference, not the secret (ADR-005).
- **Webhook signing secrets are generated by Notifex** (32 random bytes, `whsec_` prefix) and returned **once** in the create or rotate response, like an API key.

### 3. Provider catalogue (Phase 2)
Defined in code (`internal/credential/catalog.go`) with a config schema and a secret schema per provider. `GET /v1/admin/channel-providers` exposes it so the console can draw forms.

| Channel | Provider | Mode | Config | Secret |
|---|---|---|---|---|
| email | `platform` | platform | `from_name?`, `reply_to?` | — |
| email | `sendgrid` | byo | `from_email`, `from_name?` | `api_key` |
| email | `smtp` | byo | `host`, `port` (25, 465, 587, 2525), `tls` (`starttls`, `implicit`), `username?`, `from_email`, `from_name?` | `password` |
| email | `ses` | byo | `role_arn`, `region`, `from_email`, `from_name?`, `external_id` (generated by Notifex, read-only) | — (cross-account role; no stored key) |
| sms | `platform` | platform | — | — |
| sms | `twilio` | byo | `account_sid`, and `from` (E.164) or `messaging_service_sid` | `auth_token` |
| slack | `incoming_webhook` | byo | `channel_label?` | `webhook_url` (must be `https://hooks.slack.com/services/…`) |
| slack | `bot_token` | byo | `default_channel?` | `bot_token` (`xoxb-…`) |
| webhook | `signing` | byo | `url` (https, public host, port 443 or 1024–65535; added in Phase 3 slice 6, ADR-014) | generated (§2) |

Push, WhatsApp and Outlook providers, and platform Slack and Outlook (which need an OAuth install flow), are added in Phase 4. A BYO provider whose secret schema is empty (`ses`) is allowed; the database does not tie `mode` to the presence of a secret, the catalogue does, and that is unit-tested per provider.

**SES via a cross-account role**, not static keys: the tenant creates a role in their AWS account trusting the Notifex dispatcher role with the `external_id` condition. No long-lived AWS key is ever stored. The `external_id` is generated per credential and is unguessable (confused-deputy protection).

**SMTP host (SSRF):** on save, the host must be a DNS name or a public IP literal. Rejected: loopback, private (RFC 1918), CGNAT, link-local and the metadata address, IPv6 equivalents, `localhost`, and `.local`, `.internal`, `.localhost` names. No DNS lookup on the request path. Phase 3 enforces the same rule on the **resolved** address in the dialer (protects against DNS rebinding).

### 4. Explicit platform rows
A `platform` row pins a scope to Notifex's account. Example: the tenant has BYO SendGrid at tenant level, but the `dev` environment should use the platform sender. Without explicit rows that setup is impossible, because resolution would always find the tenant-level BYO row first.

### 5. Resolution
`credential.Resolve(ctx, tenant, application, environment, channel) → Ref | credential_unavailable`:
1. The first row with `status <> 'disabled'` at environment scope, then application scope, then tenant scope.
2. If there is no row: implicit platform, **only if** the channel allows platform in the ADR-005 launch matrix (email, SMS today) and the tenant is active.
3. A `platform` row (§4) or the implicit platform also requires the platform matrix to allow the channel.
4. Otherwise `credential_unavailable`.

`Ref` is `{credential_id (or none for implicit platform), mode, provider, channel}`, which Phase 3 snapshots into the run. `GET …/channel-credentials/resolve` returns the same result to the console ("which credential will this environment use?").

### 6. Status and verification
New credentials are `pending`. **`pending` and `verified` are both usable**; the console labels pending ones "unverified". Real verification (a test call to the vendor) is not built in Phase 2: calling a vendor on an API request breaks the charter (§4 "never call vendors on the request path"), and SMTP verification is an SSRF surface. Phase 3/4 adds asynchronous verification in the dispatcher, which sets `verified` or reports the vendor error.

### 7. Deletion
Hard delete, audited. A notification whose snapshot references a deleted credential fails permanently at dispatch (ADR-005). Disabling is the reversible alternative.

### 8. Permissions
Developers and above can list and read credential metadata (`credentials.view_metadata`); admins and owners create, rotate, disable and delete (`settings.manage`). Viewers see nothing. Matches docs/03.

## Consequences
- A new id kind `crd_`. One more row in the isolation table and the BOLA sweep.
- `channel_credentials` is never read by MCP or Terraform paths (credentials are portal-only, docs/12).
- Tests: secret never in responses, logs or audit (grep); AAD swap fails; crypto-shred makes secrets unreadable; every resolution order combination including disabled rows and platform rows; the partial unique index under concurrent creates; catalogue validation per provider (unknown fields, missing secret fields, SMTP host rules, Slack URL host).

## Alternatives considered
- **One credential per tenant and channel, no scopes.** Simpler, but ADR-005 requires environment and application overrides. Rejected.
- **Storing static AWS keys for BYO SES.** Long-lived keys in our database are a breach multiplier. Rejected in favour of an assumed role.
- **Synchronous verification on save.** Vendor latency and failures on the API path, and SMTP SSRF. Rejected (§6).
- **Soft delete.** Keeps secrets around after the tenant asked to remove them. Rejected; disable covers the reversible case.

## Amendment (2026-11-28, Phase 2 slice 5): implementation details
- **Uniqueness uses three partial unique indexes**, one per scope shape (tenant, application, environment), each `WHERE status <> 'disabled'`. That is equivalent to the `NULLS NOT DISTINCT` index in §1, which ent's index annotations can't express. 8 concurrent creates for one scope produce exactly one credential (tested).
- **Credentials block deleting their application or environment** (`RESTRICT`, `409`) instead of disappearing with it, so every credential removal is an explicit, audited delete.
- **Secret hint:** the last 4 characters only when the secret is at least 16 characters long. Short secrets (SMTP passwords) get no hint.
- **The AAD is (tenant, credential id, `secret_ciphertext`).** The id is generated before encryption, so the table has no id default. A ciphertext copied to another row fails to decrypt (tested), and crypto-shredding the tenant makes every secret unreadable (tested).
- **One field cipher per API process.** It caches unwrapped DEKs (ADR-006), and tenant deletion calls `Forget` on it through `tenant.Service.OnShred`. `credential.Service.Secret` decrypts for the dispatcher (Phase 3); no route calls it.
- **The ciphertext column is marked `Sensitive()`** in ent, so ent's printers never show it. Request bodies are never logged (the access log records route templates only), and the secret map is cleared after use in the handlers.
- **Checked by tests:** a lifecycle test over HTTP searches every response body, the server log and the audit trail for each secret used (SendGrid key, rotated key, Twilio token, generated signing secret) and finds none. Config emails are masked in audit records. The BOLA sweep covers ids in the query string (`resolve`) and in the body (`create`).
