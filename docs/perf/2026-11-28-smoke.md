# 2026-11-28 — Trigger smoke (local, Phase 3 slice 7)

**Scenario:** Smoke (docs/07): `make load-smoke`, 50 triggers/s arrival rate for 1 minute.
**Commit:** `feat/phase3` at 4f368ea plus the slice 7 working tree (dispatcher and k6 wiring only, no hot-path code changes).
**Environment:** one laptop (Apple M5, 10 cores; Docker Desktop with 10 CPUs and 7.7 GiB). Compose stack: Postgres 18, ElasticMQ, one API task, one dispatcher task (mock vendor, `DISPATCH_CONCURRENCY=10`), one scheduler task. k6 1.4.2 runs in a container on the compose network. Load generator and system under test share the machine, so these numbers are a **regression baseline, not capacity**.
**Workload:** the seeded `order_shipped` workflow (email + SMS on platform senders), 1 recipient and a small payload per trigger: 2 notifications per trigger, one platform-SMS reservation each.

## Verification check
`k6/verify.sql` runs after the queues drain. I checked that it can fail: with one notification set back to `retrying` it exits non-zero (`not sent: 1`); with one usage record deleted it exits non-zero (`billable without usage record: 1`); restored, it passes.

## Found while running
- **`docker-compose.yml` bug (slice 5):** the dispatcher's service-level `environment:` replaced the shared environment map instead of extending it (YAML merge keys are shallow), so the dispatcher had no `DATABASE_URL` and crash-looped. Fixed by merging `*core-env` back in.
- k6 can't reach the API through `host.docker.internal` in this Docker setup; the smoke now runs k6 on the compose network against `http://api:8080`.
